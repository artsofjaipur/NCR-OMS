### [2026-09-24 pt.5] — Meesho/Snapdeal "future date" bug root-caused + fix SQL delivered — **not yet confirmed against production**

- **User observation:** an order in the live Orders list showed "9 Dec 2026" while the actual date was still September 2026 — an impossible future date for an already-placed order.
- **Root cause, found in the one-time bulk-import Python script** (`gen_import_sql.py`, not part of this repo — see the 2026-07 order-history import project note): `parse_flex_date(a, b, y)` assumed DD/MM by default and only swapped to MM/DD when the second number was `>12`. That heuristic can't disambiguate when both numbers are `<=12` — it silently guessed DD/MM every time, which is wrong whenever the real source format was MM/DD and the day was `<=12`. Used by both `parse_meesho_date` (Meesho `Order Date`) and `parse_snapdeal_dt` (Snapdeal `ORDERCREATEDDATE`/`INVOICEDATE`/`ORDERVERIFIEDDATE`/manifest dates) — Flipkart, Amazon and Myntra's date parsers are all unambiguous formats (full month names, ISO, or a confirmed fixed M/D/YYYY) and are **not** affected.
- **Delivered `fix_meesho_snapdeal_wrong_dates.sql`** (SQL-only, not committed to this repo — same delivery pattern as the other data-migration scripts this project has needed): a read-only report of every Meesho/Snapdeal order with an impossible future `ordered_at`, followed by a targeted, provably-correct fix — day/month swap — applied **only** to rows where `ordered_at > now()` (the one case where we can independently prove the current value is wrong, since no real order is from the future). Explicitly does **not** touch any date that happens to swap into another valid past date, since that subset can't be proven wrong from the data alone — flagged to the user; offered to redo those properly from the original CSV exports if they still have them, instead of guessing.
- **Verified locally** against real imported data (reproduced the exact bug: 63 of 927 Meesho orders under the real Nyko Mart brand had a future `ordered_at`) — ran the delivered script, all 63 corrected, 0 remained in the future, and a second run changed 0 rows (idempotent).
- **Not yet confirmed against production** — waiting on the user to run it and confirm the Orders list no longer shows any 2026-12+ dates before today's actual date.
