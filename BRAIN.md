### [2026-09-11] — Fix: Company Setup only showed ONE company at a time, second company looked like it "erased" the first — Multi-company workspace switcher — **by Claude (Anthropic), delivered as a browser-upload zip (no push access to this repo/account from this session)**
- **User report (verbatim symptom):** "jitni company setup hai vo dikhni chahiye lekin nahi dikhti, ek time par ek hi dikhti hai... baar baar company change ke liye login hi thodi karta rahega" and "company save hojati hai... phir dusri company add karte hai to pahle vali ka koi ata pata nahi hota hai."
- **Root cause (confirmed by reading `src/routes/auth.ts`, `src/routes/companies.ts`, and the `users` table in `src/db/schema.ts`, not guessed):** the system was architected **one-company-per-login**. A JWT session is locked to exactly one `companyId` for its whole life (`signSession({userId, companyId, role})`), and there was no endpoint to list or switch companies once logged in. `POST /auth/register` also checks email uniqueness **globally** (`eq(users.email, body.email)`, no company scoping) even though the DB's real constraint is per-company (`uniqueIndex("users_company_email_uq").on(companyId, email)` — the schema was always designed to let the same email be an OWNER of several companies, the app just never exposed a safe way to do it). So: nothing was ever deleted or overwritten. The **first company's data was never touched** — the user simply had no way back to it except a fresh, separate signup (which `/auth/register`'s global email check would have blocked anyway) or a real logout/login with different credentials, and "add second company" with the same email had no real endpoint at all before this fix.
- **Fix — three new endpoints, no destructive change to anything existing:**
  - `POST /companies` (`src/routes/companies.ts`, OWNER-only) — creates an **additional** company under the **same email + same existing password hash** as the caller's current session (never a new signup, never touches `/auth/register`'s public path). Inserts the company, a default warehouse, and a new per-company `users` row, then hands back a session token already switched to the new company — no extra login step.
  - `GET /auth/my-companies` (`src/routes/auth.ts`, any logged-in role) — looks up the current session's email, lists every company where that email has an active `users` row, and flags which one is `current`.
  - `POST /auth/switch-company` (`src/routes/auth.ts`) — re-issues a JWT scoped to a different company, but **only** if the current session's email has its own active user row there (403 otherwise — never a way to hop into someone else's company). No password re-entry: the existing bearer token already proves the password was checked once, same trust boundary any "switch account" menu uses.
- **Frontend (`public/nav.js` + `public/nav.css`):** sidebar profile block gets a workspace `<select>` (hidden entirely when there's only one company — a single-company workspace sees zero visual change), populated from `GET /auth/my-companies`; switching fires `POST /auth/switch-company`, updates `sessionStorage.ncr_auth`, and reloads so every panel refetches for the new company. OWNER role also gets a **"+ Add Company"** button (`window.prompt()` for the legal name → `POST /companies`) — ADMIN/OPS/VIEWER can switch between companies they already belong to but cannot create new ones.
- **Why this is safe by construction:** creating/switching is strictly scoped to rows sharing the exact same email as the current session (reusing the DB's own genuine per-`(companyId,email)` design, not fighting it); the public `/auth/register` endpoint's global email-uniqueness check was deliberately left untouched (loosening it would be a hijack risk — anyone could register into someone else's email without proving password ownership).
- **No new database migration needed** — this is pure application/route + frontend code, unlike the returns.return_type/reason change above which does need `drizzle/0004_return_type_reason.sql` applied.
- **Verification — live end-to-end against a real, disposable local PostgreSQL 16 (spun up in-sandbox specifically for this, not just tsc/vitest):**
  ```
  npx drizzle-kit push --force        → schema pushed clean
  register (company A, OWNER)         → 201, token A issued
  POST /companies (company B)         → 201, token B issued (same email)
  POST /companies (company C)         → 201, token C issued (same email)
  GET /auth/my-companies (token A)    → 200, all 3 companies listed, "current": true only on A
  PATCH /companies/me (token A, profile fields) → 204
  POST /auth/switch-company → B, then switch back → A
  GET /companies/me (token A, after B/C existed) → 200, ALL of A's earlier profile fields intact
  unauthorized switch-company to a company with no user row for this email → 403 "You don't have an account in that company"
  ```
  All results correct — A's data was never lost or overwritten at any point, and the negative/security case (cross-company switch) is correctly rejected.
  Also verified: `npx tsc -p tsconfig.json --noEmit` → 0 errors; `node --check public/nav.js` → syntax OK; `npx vitest run tests/ingestion.test.ts tests/security.test.ts` → 18/18 pass.
